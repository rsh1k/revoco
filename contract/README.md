# The decision contract

Two runtimes evaluate the same decision. A gate that says *allow* in Go and
*require approval* in Python is worse than no gate at all, because it produces a
record that cannot be trusted in either direction. Everything in this directory
exists to make that divergence impossible to ship.

## Who decides what

The split is not "Go is the fast one and Python is the slow one". They answer
genuinely different questions, and the boundary is drawn where the information
lives.

| | Enforcer (Go) | Control plane (Python) |
|---|---|---|
| Runs | in the request path, per tool call | out of band |
| Needs | a policy bundle and the call | filesystem, snapshots, model, corpus |
| Decides | which rule matches, and the effect | what the rules should be |
| Classifies reversibility | from the bundle's static registry | from live state |
| Detects phantom rollback | **no** | yes |

That last row is the important one. A *phantom rollback* is an action claiming an
undo that cannot actually execute — the snapshot was never taken, the inverse was
never wired up. Catching it requires reading the world, so it belongs to the
control plane. The enforcer is told the reversibility; it does not discover it.

Being explicit about that beats implying the sidecar checks something it cannot.
A control that is documented as narrower than it looks is honest; one documented
as wider than it is will be believed exactly once.

## The bundle

The control plane compiles a revoco `Policy` plus an `InverseRegistry` into a
single portable document. The enforcer loads it and evaluates it. The enforcer
never parses Python, never imports revoco, and has no opinion of its own.

```json
{
  "schema": 1,
  "policy_id": "retie-default@1",
  "default_effect": "deny",
  "reversibility": { "invoices.read": "reversible", "payments.wire": "irreversible" },
  "unknown_tool_reversibility": "unknown",
  "rules": [
    { "id": "reads-are-free", "effect": "allow", "tools": ["*"], "actions": ["read"],
      "agents": ["*"], "require_roles": [], "reversibility": [],
      "min_risk": null, "max_risk": null, "min_threat_score": null,
      "reason": "observing changes nothing" }
  ]
}
```

Fields are spelled out rather than defaulted. A missing `tools` in revoco means
`["*"]`, and relying on two languages to agree about an absent field is exactly
the class of bug this contract exists to prevent — so the compiler writes every
field explicitly and the enforcer refuses a rule that omits one.

## Matching semantics

Rules are evaluated in order and the **first match wins**, like a firewall. A rule
matches when *all* of these hold:

1. `tool` glob-matches one of `tools`
2. `action` glob-matches one of `actions`
3. `agent_id` glob-matches one of `agents`
4. every role in `require_roles` is held by the principal
5. `reversibility` is empty, or the call's reversibility is in it
6. `min_threat_score` is null, or `threat_score >= min_threat_score`
7. `min_risk` is null, or `risk >= min_risk`
8. `max_risk` is null, or `risk <= max_risk`

If no rule matches, the effect is `default_effect`.

Globs are `fnmatch` with case sensitivity — Go's `path.Match` differs from Python's
`fnmatch` on character classes and on `/`, so the enforcer implements the Python
semantics directly rather than borrowing the standard library's. The conformance
fixtures include cases that separate the two.

## Deliberately not in the bundle, yet

**Conditions and budgets.** revoco rules can carry an argument-aware `condition`
and a spend `budget` that participates in matching. Both are expressible, and
neither is in schema 1 — a rule using them is rejected at compile time rather
than silently compiled into something weaker. Refusing to compile is the only
safe failure here: a bundle that quietly dropped a condition would widen a rule
without anyone noticing.

## The oracle

`conformance/fixtures/*.json` are golden files: inputs and the verdict the Python
gate actually produced for them, generated by running revoco rather than by
writing down what it ought to do. Both runtimes must reproduce every one.

This is the same discipline that verified the Rust-to-Python port of `detent`,
where the two implementations were held together by making the numbers match. It
worked there because the fixtures came from execution, not from intent.
